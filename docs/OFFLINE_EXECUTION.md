# Offline Execution Boundary

## 1. Assurance dimensions

Evidence Review System separates application offline behavior, optional OS isolation, and human process attestation. These are **independent assurance dimensions**: passing one never implies another.

### `APPLICATION_OFFLINE_GUARD`

The packaged Python runtime installs an application-level network guard before command dispatch. It blocks project/runtime access to non-loopback TCP/UDP and prohibited network/process APIs while allowing the protected local review server.

Allowed local communication includes:

- IPv4 loopback `127.0.0.0/8`;
- IPv6 loopback `::1`;
- `localhost`;
- supported Unix-domain/local sockets.

The formal review workflow, metrics, page image cache, Track handoffs, HTML, and human decision records require no external API.

Static process scanning has one narrow exception: `evidence_review/review_packet/browser_launcher.py` may use `subprocess` only to start the protected loopback review-server child process. The exception does not allow HTTP clients, remote network access, `os.system`, or subprocess use in another source path. PDF page rendering is in-process and does not use an external `pdftoppm` process.

Application-only validation records:

```text
assurance_level: APPLICATION_OFFLINE_GUARD
cryptographic_network_isolation_verified: false
```

This is intentionally not a claim that the operating system cryptographically prevented all network traffic.

### `OS_ISOLATED`

This is a separate operating-system assurance level, for example Windows outbound firewall policy, a networkless container, a network namespace, or an isolated VM. Application validation alone never claims `OS_ISOLATED`. `cryptographic_network_isolation_verified` may become true only when the deployment's separate OS/network-isolation evidence actually supports that claim.

### `PROCESS_ATTESTATION`

Release process attestation is separate from a per-run human review decision. It records that a named reviewer examined a specific release candidate and packet. It is not cryptographic identity proof. Current process metadata therefore keeps `cryptographic_identity_verified: false`.

## 2. Protected loopback review server

The final Review Workspace is served only on loopback with a run-scoped URL-safe token. A normal protected URL is:

```text
http://127.0.0.1:<port>/runs/<RUN-ID>/<TOKEN>/review
```

The same protected prefix is used for packet, packet-hash, decision, and decision-status endpoints.

Security rules:

- exact loopback bind;
- exact Host validation;
- same-origin Origin validation for state-changing requests;
- no permissive CORS;
- bounded JSON request body;
- `application/json` only for decision POST;
- run-scoped token comparison;
- symlink/reparse-point rejection for protected artifacts;
- final review unavailable until packet and HTML both exist.

Local loopback traffic is permitted by `APPLICATION_OFFLINE_GUARD`; permitting it does not permit external network access.

## 3. Detached server lifecycle

`review-run serve` starts a detached protected server with a 2-second readiness timeout.

```powershell
evidence-review review-run serve `
  --workspace <workspace> `
  --run-id <RUN-ID> `
  --reviewer-id <REVIEWER-ID> `
  --detach `
  --idle-timeout-seconds 5

evidence-review review-run serve-status `
  --workspace <workspace> `
  --run-id <RUN-ID>

evidence-review review-run serve-stop `
  --workspace <workspace> `
  --run-id <RUN-ID>
```

The default idle timeout is 1800 seconds (30 minutes), measured from the last valid protected activity with `time.monotonic()`. Rejected or malformed requests do not refresh it.

The run-scoped state file is management metadata, not review authority. Stale state must be removed. PID reuse protection must prevent `serve-stop` from signaling an unrelated process.

Windows and POSIX process identity mechanisms differ. Windows liveness uses a non-destructive process query before command-line/token identity validation. Acceptance must still test Windows explicitly on the exact target commit; an unexecuted Windows lifecycle check is `NOT_RUN`, not a PASS inferred from POSIX behavior.

## 4. Human decision boundary

The protected UI displays only decision and notes as ordinary reviewer inputs. Reviewer ID and packet hash are session/runtime context; `reviewed_at` is generated by the server.

Decision request v2 fields:

```json
{
  "reviewer_id": "reviewer-01",
  "packet_hash": "<current-packet-sha256>",
  "decision": "SATISFIED",
  "notes": "review notes"
}
```

The server recomputes the current packet hash before writing and produces an offset-aware ISO-8601 timestamp. A valid decision is written create-only under `human-decisions/`. The machine packet and HTML remain immutable.

`review.html` opened with `file:` cannot write through the server. Its downloaded five-field envelope is only a transport artifact. Import uses:

```powershell
evidence-review review-run import-decision `
  --workspace <workspace> `
  --run-id <RUN-ID> `
  --envelope <human-decision-envelope.json>
```

Import rejects stale packet hashes and create-only collisions.

## 5. Runtime metrics are non-authoritative

`run-metrics-events/` and derived `run-metrics.json` are local observability artifacts. They record deterministic stage timing, Track A/B external wait, failures, retry attempts, server startup, and browser dispatch.

They must not alter or participate in:

- Run ID;
- review request authority;
- evidence hashes;
- run manifest authority;
- final packet hash;
- human decision packet binding.

Telemetry may be deleted or regenerated from its immutable events without changing the review result. Missing metrics fail the performance acceptance gate but do not silently modify packet authority.

## 6. Application guard scope

The application-level guard is not a complete sandbox. It does not prove security against:

- a hostile or modified Python interpreter;
- a native extension or arbitrary external binary outside the audited runtime boundary;
- connections opened before guard installation;
- other users/admin processes;
- filesystem tampering after validation;
- arbitrary scripts outside the packaged runtime.

Use OS isolation when those threats are in scope.

The runtime policy blocks non-loopback forms of operations such as:

```text
socket.create_connection(remote)
socket.socket.connect(remote)
socket.socket.connect_ex(remote)
socket.socket.sendto(..., remote)
```

Resolver policy accepts localhost or literal loopback addresses only. Loopback and local sockets remain available for the review server.

## 7. Static source and release path policy

Release/runtime scanning rejects prohibited network/process clients and unsafe dynamic access patterns according to the repository offline policy. Release manifest paths must remain safe relative paths below the workspace; absolute paths, traversal, drive-prefixed paths, and unsafe backslash forms are rejected.

Final release output validation reads `bundle-manifest.json` and `runtime-manifest.json` from the final archive **without extracting** it. It verifies manifest membership, unique paths, **case-fold collisions**, byte sizes, and SHA-256 values against the final ZIP bytes. Any mismatch produces `RELEASE_OUTPUT_VALIDATION_FAILED`; `PROCESS_ATTESTATION` cannot override that failure.

## 8. Windows OS isolation example

When OS-level network isolation is required, an administrator can apply an outbound block to the exact Python/runtime executable and retain the rule as operational evidence.

```powershell
New-NetFirewallRule `
  -DisplayName "Evidence Review Offline" `
  -Direction Outbound `
  -Program "C:\path\to\python.exe" `
  -Action Block

Get-NetFirewallRule -DisplayName "Evidence Review Offline"
```

The protected localhost browser route must be tested in the same deployment configuration. The current automated validator does not prove the host firewall policy.

## 9. Container isolation example

```bash
docker run --rm --network none \
  -v "$PWD/workspace:/workspace" \
  evidence-review:local \
  evidence-review --help
```

Retain the exact container command as OS-isolation evidence when claiming that assurance level.

## 10. Runtime provenance diagnostics

Run the dependency-safe diagnostic surface with the exact supported interpreter that will run the review. It is intentionally stdlib-only and executes before business imports:

```powershell
$Workspace = "C:\evidence-review-workspace"
py -3.13 -m evidence_review doctor --repository-root .
py -3.13 -m evidence_review review-question prepare --workspace $Workspace --question "<question>"
```

`SOURCE_MISMATCH` blocks business commands until the intended checkout is active. Use an interpreter-pinned editable install to remediate it:

```powershell
py -3.13 -m pip install -e ".[dev]"
```

`DEPENDENCY_MISSING` is a structured diagnostic, not a traceback. Record the JSON output before changing the environment.

## 11. Current release acceptance checks

From a clean Windows checkout at the exact acceptance HEAD, record:

- Python 3.13 version and runtime provenance;
- documentation integrity result;
- pytest, Ruff, mypy, compileall;
- focused formal-review suites;
- protected browser success and browser-open failure;
- `serve-status` / `serve-stop`, stale state, idle process behavior;
- protected human decision and `REVIEW_COMPLETED` projection;
- archival envelope download and `import-decision`;
- 1366×768, 1920×1080, 3840×2160;
- 100%, 200%, fit-to-page browser zoom;
- three simple-question metrics runs and p50/p95;
- final packet, HTML, metrics, and decision-record hashes.

Unsupported Python versions are not release gates. Do not convert an unexecuted check into PASS. GitHub Actions state is reported independently as actually observed.

## 12. Release process attestation

Release authorization uses the strict `evidence-review/human-attestation` process contract and a create-only `human-attestation.json`. It validates named reviewer metadata, offset-aware review time, exact **release candidate hash**, exact **packet hash**, required checklist PASS evidence, and append-only creation. A valid process record may carry `REVIEWED_AND_ACCEPTED_FOR_RELEASE` only after all required release gates have passed.

`PROCESS_ATTESTATION` remains process assurance, not cryptographic identity assurance. `cryptographic_identity_verified` remains `false` in the current design.
