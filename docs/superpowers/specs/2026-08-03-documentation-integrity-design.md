# Repository-wide Documentation Integrity Design

> Document status: CURRENT

Issue: #50  
Parent epic: #27  
Approved: 2026-08-03

## 1. Purpose

The repository must detect stale, broken, unsafe, or misleading documentation before a release is accepted. The documentation integrity subsystem validates all current Markdown, selected historical records, and registered generated Markdown without network access or command execution.

The subsystem produces deterministic evidence that documentation references the current repository and current command-line interface accurately. A documentation error must fail workspace validation and block release even when process attestation is otherwise valid.

## 2. Goals

The implementation must:

1. Discover and classify every Markdown document under the approved repository scope.
2. Validate current internal links, heading anchors, repository file references, module references, and supported command examples.
3. Preserve historical records without rewriting them to match current implementation details.
4. Render and validate Markdown generated by Python code, including the Codex bundle `VALIDATE.md` and ChatGPT web runtime `PROJECT_INSTRUCTIONS.md`.
5. Produce a create-only canonical JSON report with stable findings and counts.
6. Expose `evidence-review documentation validate` as the canonical entry point.
7. Integrate fail-closed with workspace validation and release building.
8. Operate offline and deterministically on Windows and Linux.

## 3. Non-goals

This work does not:

- request external URLs or test their current availability;
- execute commands copied from Markdown;
- restore missing legacy wrapper scripts;
- rewrite historical evidence to use current commands, branches, or file names;
- enforce prose style, spelling, formatting, or general Markdown aesthetics;
- replace the existing runtime, rule, golden, Grist QA, lineage, or human-attestation contracts;
- provide cryptographic identity verification or deployment signing.

## 4. Approved policy decisions

The following decisions are fixed for Issue #50:

- Missing legacy script references are removed or replaced with current canonical `evidence-review` commands. Legacy wrapper scripts are not restored.
- Scope includes `README.md`, `AGENTS.md`, `docs/**/*.md`, `skills/**/SKILL.md`, and explicitly registered generated Markdown.
- External URLs are checked only for valid `https://` syntax. No network request is permitted.
- Command examples are validated statically. They are never executed by the documentation validator.
- Historical records use path-based defaults plus explicit overrides.
- `ERROR` findings fail validation. `WARNING` findings remain visible but do not fail validation by default.
- The result is a canonical JSON artifact plus a concise stdout summary.
- Configuration is repository-owned, strict, and versioned.

## 5. Architecture

The subsystem is isolated under one package:

```text
src/ansim_review/documentation_integrity/
├─ __init__.py
├─ contract.py
├─ discovery.py
├─ classification.py
├─ markdown.py
├─ commands.py
├─ generated.py
├─ validator.py
└─ cli.py
```

Each module has one responsibility:

- `contract.py` decodes strict configuration and defines immutable finding and report models.
- `discovery.py` enumerates repository Markdown and detects unclassified documents.
- `classification.py` applies current/historical roots and path overrides.
- `markdown.py` extracts links, headings, fragments, file references, external URLs, and fenced command blocks.
- `commands.py` performs static command and option validation.
- `generated.py` imports and invokes registered Markdown generator functions.
- `validator.py` orchestrates discovery, parsing, checking, finding normalization, and report construction.
- `cli.py` writes the create-only report, prints the summary, and returns the process exit code.

The public interface is narrow:

```python
def validate_documentation(
    repository_root: Path,
    config_path: Path,
) -> DocumentationIntegrityReport:
    ...
```

The function does not write files. File creation and overwrite protection belong to the CLI layer and release integration.

## 6. Configuration contract

The authority file is `documentation-integrity.json` at the repository root.

Its strict contract is:

```json
{
  "format": "evidence-review/documentation-integrity-config",
  "version": 1,
  "current_roots": [
    "README.md",
    "AGENTS.md",
    "docs",
    "skills"
  ],
  "historical_roots": [
    "docs/acceptance",
    "docs/superpowers/plans",
    "docs/superpowers/specs"
  ],
  "current_overrides": [],
  "historical_overrides": [],
  "generated_documents": [
    {
      "id": "CODEX_VALIDATE",
      "generator": "ansim_review.packaging.codex_bundle:render_validation_document",
      "virtual_path": "codex-workspace/VALIDATE.md",
      "classification": "CURRENT"
    },
    {
      "id": "WEB_PROJECT_INSTRUCTIONS",
      "generator": "ansim_review.packaging.project_instructions:render_project_instructions",
      "virtual_path": "chatgpt-web-runtime/PROJECT_INSTRUCTIONS.md",
      "classification": "CURRENT"
    }
  ]
}
```

### 6.1 Strict decoding

The decoder must reject:

- unknown top-level or nested fields;
- an unsupported format or version;
- duplicate JSON keys;
- duplicate paths or generated document IDs;
- absolute paths;
- backslash paths;
- empty path components;
- `.` or `..` components;
- paths that resolve outside the repository;
- invalid Python generator references;
- classifications other than `CURRENT` or `HISTORICAL`.

### 6.2 Classification precedence

Classification order is deterministic:

1. exact or most-specific explicit override;
2. most-specific historical/current root;
3. otherwise unclassified.

A path matching current and historical definitions at the same specificity is `CONFIG_CLASSIFICATION_CONFLICT`.

Any discovered in-scope Markdown with no classification is `DOCUMENT_CLASSIFICATION_MISSING` and is an `ERROR`.

## 7. Document classes

### 7.1 Current documents

Current documents describe the repository or workflow as it exists now. They receive full validation:

- internal target existence;
- heading fragment existence;
- repository file, image, attachment, script, and module existence;
- supported command, subcommand, and option existence;
- safe relative paths;
- valid external URL scheme;
- generated document renderability.

### 7.2 Historical documents

Historical documents preserve acceptance evidence, past plans, and past specifications. Their old commit SHAs, branches, generated file paths, and command behavior are not required to remain current.

Historical documents are checked for:

- malformed Markdown link syntax detectable by the parser;
- repository path escape;
- absolute repository references presented as reusable repository paths;
- unsafe backslash repository references;
- external URL scheme;
- historical status marker.

The first non-empty line should be:

```markdown
> Document status: HISTORICAL RECORD
```

A missing marker is `HISTORICAL_MARKER_MISSING` with severity `WARNING`. It does not fail validation by itself. This preserves existing evidence while making ambiguous status visible.

Current documents that link to historical records must label the link or surrounding text as historical. Otherwise the validator emits `CURRENT_TO_HISTORICAL_REFERENCE_UNMARKED` as an `ERROR`.

## 8. Markdown discovery and parsing

### 8.1 Repository discovery

Discovery includes:

```text
README.md
AGENTS.md
docs/**/*.md
skills/**/SKILL.md
```

Only regular files are accepted. Symlinks resolving outside the repository are rejected. Discovery results are normalized to canonical POSIX relative paths and sorted bytewise.

Generated documents are not represented by repository files. They are appended from the configuration registry using their virtual paths.

### 8.2 Structural extraction

The parser extracts:

- ATX and Setext headings;
- inline links and images;
- reference-style link definitions and uses;
- same-document fragments;
- cross-document fragments;
- raw external URLs where reliably identifiable;
- fenced code blocks and their language labels;
- the source line and column for every extracted item.

Markdown code spans and non-command fenced blocks must not be treated as links or commands unless the syntax explicitly creates a link.

### 8.3 Heading anchors

Heading anchors use one documented normalization function shared by validation and tests. The function must cover:

- Unicode text;
- case folding consistent with repository documentation policy;
- whitespace-to-hyphen conversion;
- punctuation removal;
- duplicate heading suffixes.

A missing target fragment is `INTERNAL_LINK_ANCHOR_MISSING`.

Duplicate headings that generate ambiguous anchors produce `DUPLICATE_HEADING_ANCHOR` as a `WARNING`, unless an actual link resolves ambiguously, in which case it is an `ERROR`.

## 9. Link and path validation

### 9.1 Internal references

For current documents, the validator resolves relative links from the containing document directory and verifies the target under the repository root.

Representative errors include:

```text
INTERNAL_LINK_TARGET_MISSING
INTERNAL_LINK_ANCHOR_MISSING
REPOSITORY_PATH_ESCAPE
ABSOLUTE_REPOSITORY_PATH
BACKSLASH_REPOSITORY_REFERENCE
CURRENT_TO_HISTORICAL_REFERENCE_UNMARKED
```

Directory links are valid only when the directory exists. Links to generated virtual documents are valid only when the virtual path is registered.

Query strings do not affect file existence. Fragments are validated separately.

### 9.2 External URLs

Allowed external URLs must use `https://` with a non-empty host. The validator does not perform DNS lookup, HTTP requests, redirects, certificate checks, or status-code checks.

Invalid schemes, including `http://`, `ftp://`, and protocol-relative URLs, produce `EXTERNAL_URL_SCHEME_INVALID`. This is a `WARNING` unless the URL is presented as a required security, installation, or release command dependency in a current document; those cases are `ERROR`.

Mail addresses and repository-local fragments are not external URLs.

## 10. Static command validation

### 10.1 Eligible blocks

Command analysis applies to fenced blocks labelled:

```text
powershell
pwsh
bash
sh
shell
console
text
```

A `text` block is analyzed only when a line begins with a recognized executable. Continuation syntax for PowerShell backticks and POSIX backslashes is normalized before parsing.

### 10.2 Recognized command families

The initial registry supports:

```text
evidence-review ...
python -m ansim_review ...
python -m evidence_review ...
pytest ...
python -m pytest ...
ruff check ...
python -m ruff check ...
mypy ...
python -m mypy ...
python -m compileall ...
```

Unrecognized general shell commands are not executed and are not semantically validated. File/script references in those commands are still checked when they clearly name repository-local `.py`, `.ps1`, `.sh`, or `.bat` files.

### 10.3 CLI parser validation

`evidence-review` and the Python module entry points use the real parser construction function in validation-only mode. The validator verifies:

- command and nested subcommand existence;
- option existence;
- required option presence;
- missing option values;
- mutually exclusive argument conflicts where argparse exposes them;
- removed legacy command or script names.

Parser validation must not dispatch a command handler.

### 10.4 Tool option validation

For pytest, Ruff, mypy, and compileall, validation uses a bounded project-owned option registry rather than executing the tools. The registry includes only options used in repository documentation and tests. Adding a new documented option requires adding it to this registry and its tests.

### 10.5 Placeholders

The following forms are explicit placeholders:

```text
<path>
<output>
<SHA256>
${WORKSPACE}
$WORKSPACE
$env:WORKSPACE
%WORKSPACE%
```

Placeholders satisfy value presence but do not satisfy target existence. A command that relies on a placeholder is structurally validated without resolving that value.

Unknown angle-bracket or variable-like placeholders produce `COMMAND_PLACEHOLDER_AMBIGUOUS` as a `WARNING`.

## 11. Generated Markdown

Each configured generator uses the form:

```text
package.module:function
```

The validator imports the module, resolves the function, invokes it without arguments, and requires a `str` result. The render is held in memory and validated under its configured virtual path and classification.

Failures are represented as findings rather than uncaught exceptions:

```text
GENERATED_DOCUMENT_IMPORT_FAILED
GENERATED_DOCUMENT_CALLABLE_MISSING
GENERATED_DOCUMENT_RENDER_FAILED
GENERATED_DOCUMENT_RESULT_INVALID
```

### 11.1 Codex `VALIDATE.md`

`ansim_review.packaging.codex_bundle` must expose:

```python
def render_validation_document() -> str:
    ...
```

`build_codex_bundle()` writes that exact string to `VALIDATE.md`.

The document must describe a real offline validation sequence and include at least:

```powershell
python -m ansim_review --help
python -m ansim_review rules --help
python -m ansim_review source-batch --help
python -m ansim_review documentation validate --help
python -m compileall -q src
```

The final implementation plan may add stronger repository-supported checks, but it must not return to a single generic `--help` command.

### 11.2 Web project instructions

`render_project_instructions()` remains the canonical generator for `PROJECT_INSTRUCTIONS.md`. The documentation validator verifies its commands and references without running bootstrap or runtime code.

## 12. Finding contract

A finding contains exactly:

```json
{
  "severity": "ERROR",
  "code": "INTERNAL_LINK_TARGET_MISSING",
  "document_path": "docs/VALIDATE.md",
  "line": 18,
  "column": 7,
  "target": "../scripts/validate_workspace.py",
  "message": "Referenced repository file does not exist."
}
```

Allowed severities are `ERROR` and `WARNING`.

Findings are deduplicated by their complete canonical tuple and sorted by:

```text
severity rank
document_path
line
column
code
target
message
```

`ERROR` sorts before `WARNING`.

Messages are stable project-owned strings. They must not include platform-specific absolute paths, exception repr output, memory addresses, or nondeterministic ordering.

## 13. Report contract

The report format is:

```json
{
  "format": "evidence-review/documentation-integrity-report",
  "version": 1,
  "status": "FAIL",
  "document_count": 84,
  "current_document_count": 31,
  "historical_document_count": 51,
  "generated_document_count": 2,
  "error_count": 3,
  "warning_count": 5,
  "findings": []
}
```

The exact allowed keys are fixed by the strict v1 contract.

Rules:

- `ERROR > 0` means `status=FAIL` and CLI exit code `1`.
- no errors means `status=PASS` and CLI exit code `0`.
- warnings do not change `PASS` to `FAIL`.
- counts are derived, not caller-supplied.
- generated documents are included in `document_count` and separately counted.
- serialization uses existing canonical JSON utilities.
- identical repository bytes, configuration bytes, and generator outputs produce byte-identical reports.

Configuration decoding failures produce a canonical report with an appropriate `CONFIG_*` finding when enough configuration context exists to write a report. A missing or unreadable authority config causes a concise CLI error and exit code `2`, because report classification rules cannot be trusted.

## 14. CLI

Canonical command:

```powershell
evidence-review documentation validate `
  --repository-root . `
  --config documentation-integrity.json `
  --output build/documentation-integrity-report.json
```

The CLI must:

1. resolve all paths under the explicit repository root;
2. reject an existing output path;
3. run validation without executing Markdown commands;
4. write canonical report bytes with create-only semantics;
5. print a concise stable summary;
6. return `0` for PASS, `1` for a report containing errors, and `2` for invocation or authority-config failure.

Example stdout:

```text
Documentation integrity: FAIL
Documents: 84 current=31 historical=51 generated=2
Findings: errors=3 warnings=5
Report: build/documentation-integrity-report.json
```

## 15. Workspace and release integration

### 15.1 Workspace validator

`validate_release_workspace()` invokes the same validation engine using the repository authority config.

A failed documentation report adds:

```text
DOCUMENTATION_INTEGRITY_FAILED
```

The workspace report includes the documentation report payload or a stable summary field according to the existing workspace report compatibility constraints. The integration must not create a report file during pure validation.

### 15.2 Release builder

The release order remains:

```text
workspace validation
→ release output validation
→ process attestation validation
→ release decision
```

A documentation integrity error causes workspace failure and release `BLOCKED`.

The release reason codes include both:

```text
AUTOMATED_VALIDATION_FAILED
DOCUMENTATION_INTEGRITY_FAILED
```

The release manifest must set:

```json
{
  "status": "BLOCKED",
  "tag_allowed": false
}
```

A valid process attestation cannot remove or downgrade documentation findings.

## 16. Determinism and platform behavior

The validator must be byte-deterministic across supported Windows and Linux environments.

It therefore uses:

- POSIX repository-relative paths in contracts;
- explicit UTF-8 decoding;
- stable newline handling;
- stable discovery and finding sorting;
- no filesystem modification-time fields;
- no current timestamps in reports;
- no network calls;
- no command execution;
- no platform-specific absolute paths in messages;
- generator output bytes rather than generated temporary file metadata.

Case-sensitive repository identity is preserved. A separate case-fold collision check detects links that would resolve ambiguously on Windows.

## 17. Security and fail-closed behavior

The subsystem treats documentation as untrusted input.

It must not:

- follow a symlink outside the repository;
- import arbitrary generators not listed in the authority config;
- dispatch argparse handlers;
- evaluate shell syntax;
- execute code blocks;
- interpolate environment variables;
- access network resources;
- overwrite an existing report.

Parser or generator exceptions become stable findings. Only authority failures that make classification impossible use exit code `2` without a report.

## 18. Migration strategy

Implementation proceeds without restoring legacy wrappers.

1. Add contracts and validator against small fixtures.
2. Register current and historical path policy.
3. Render generated documentation through explicit functions.
4. Run the validator against the real repository and record all findings.
5. Correct current documentation only:
   - replace removed script references with canonical CLI commands;
   - repair current internal links and fragments;
   - clarify links from current documents to historical records;
   - expand generated `VALIDATE.md`.
6. Add historical markers without altering historical evidence content.
7. Integrate workspace and release gates.
8. Preserve a deterministic acceptance report for Issue #50.

Historical documents are not rewritten solely because a past command or branch no longer exists.

## 19. Testing strategy

### 19.1 Unit tests

Unit coverage includes:

- strict config decoding and duplicate JSON keys;
- safe path normalization and classification precedence;
- classification conflict and missing classification;
- Markdown headings, links, references, fragments, and code fences;
- Unicode and duplicate anchor normalization;
- path escape, absolute path, backslash path, symlink escape, and case-fold collision;
- external URL scheme;
- current-to-historical link labeling;
- command continuation normalization;
- argparse command, subcommand, option, and required argument validation;
- bounded pytest/Ruff/mypy/compileall registries;
- placeholder recognition and ambiguity;
- generated document import/render failures;
- finding sorting and deduplication;
- strict report decoding and canonical bytes;
- create-only report writing and exit codes.

### 19.2 Integration tests

Integration coverage includes:

- scanning the actual repository scope;
- rendering and validating both generated documents;
- detecting a removed legacy script in a current fixture document;
- allowing an old SHA, branch, or file reference in a historical fixture;
- warning on a missing historical marker;
- producing byte-identical reports on repeated runs;
- failing workspace validation for a documentation error;
- blocking release despite a valid process attestation;
- validating the generated Codex bundle `VALIDATE.md` inside the final bundle.

### 19.3 Full verification

Completion requires:

```text
full pytest
Ruff
strict mypy
compileall
Python 3.11 wheel
Python 3.13 wheel
Windows workspace validator
Ubuntu workspace validator
```

GitHub Actions unavailability must be reported accurately and must not be represented as a CI pass.

## 20. Acceptance criteria

Issue #50 is complete only when:

1. Every in-scope Markdown document is deterministically classified.
2. Every current internal link, file reference, and fragment resolves.
3. Every supported current CLI example passes static semantic validation.
4. Historical records remain intact and are visibly classified.
5. Registered generated Markdown renders and validates successfully.
6. Codex `VALIDATE.md` contains the approved offline validation sequence.
7. The report is strict, create-only, canonical, and byte-reproducible.
8. An error returns CLI exit code `1` and fails workspace validation.
9. Release is `BLOCKED` with `tag_allowed=false` when documentation validation fails.
10. A process attestation cannot override the failure.
11. Existing golden, rule approval, active manifest, Grist QA, and lineage artifacts remain unchanged.
12. Required automated and platform validation passes or is explicitly recorded as unavailable.

## 21. Implementation boundary

This design authorizes planning, not implementation. Code changes begin only after this specification is reviewed and the implementation plan is approved.
